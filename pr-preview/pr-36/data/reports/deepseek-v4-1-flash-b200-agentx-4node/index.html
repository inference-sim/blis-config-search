Serving DeepSeek-V4.1-Flash to coding agents on 4 B200 nodes

A configuration search over 252 BLIS replay runs on 32× B200, driven by the recorded AgentX agentic traffic rather than a synthetic request shape. The winner is 8x TP4 + EP at 1,465.1 output tok/s (45.8 per GPU) while every user still reads at 131.4 tok/s.

BLIS discrete-event simulationblis-latency-kernel v0.3.0AgentX MVP replay (393 recorded Claude Code trajectories)32× B200 · 4 nodes

What was tested

The 12 highest-ranked of 19 valid expert-parallel and tensor-parallel layouts that fill 32 GPUs, probed up a session-lane ladder and refined one engine knob at a time — 252 runs, 12 candidate topologies, 24 refinement arms, 36 servable finalists, 0 shapes the simulator refused or that missed the floor.

What was found

This is a prefill-dominated workload: 90,449 input tokens per request against 916 output, about 99:1. Output tok/s per GPU reads low by chatbot standards because almost all the work is reading context — the winner is ingesting roughly 144,666 input tok/s.

What to run

8x TP4 + EP at 102 concurrent agent sessions (80% of the highest load tested (128); capacity was not bracketed, so this is a lower bound). The non-EP controls do run on this part; compared at the highest load both arms serve, expert parallelism is worth -0.3% to +5.4%. Where it earns its place is capacity, not per-token speed.

1The measurements

Each row below is one BLIS replay run. The load axis is session-tree lanes, not in-flight requests: one lane drives a whole agent trajectory that fans out into many sub-requests, so a lane is worth far more concurrency than a single chat turn.

The interactivity floor is the default 50 tok/s per user (ITL p99 ≤ 20 ms).

2The operating curve, and where it stops

Throughput climbs almost linearly with lanes and was still climbing at the last load tested — no cliff was observed for this shape, because the ramp ended first. 8x TP4 + EP holds 115.0 tok/s per user at 128 lanes.

The recommendation is 102 lanes rather than the 128 this shape was last seen serving, because a deployment needs headroom for a burst and this workload's bursts are whole agent trajectories waking up at once. Note the ceiling itself is unbracketed here: the shape never missed the floor, so its true capacity is somewhere above 128 lanes.

3Expert parallelism helps here — but it is not what rescues the fit

5 of the 7 expert-parallel candidates have their non-EP control in the sweep, and each such pair is run together, so the direction is measured rather than assumed. On B200 the controls do run. Compared at the highest load both arms served, expert parallelism is worth between -0.3% and +5.4% — modest. Where it earns its place is capacity: it raises the servable ceiling, which is a different claim from being faster per token:

  • 4x TP4xDP2 + EP: +5.4% at a matched 64 lanes (27.9 vs 26.4 tok/s/GPU)
  • 4x TP2xDP4 + EP: +3.2% at a matched 16 lanes (6.1 vs 5.9 tok/s/GPU)
  • 8x TP4 + EP: +2.5% at a matched 128 lanes (60.7 vs 59.2 tok/s/GPU)
  • 4x TP1xDP8 + EP: +0.0% at a matched 8 lanes (4.0 vs 4.0 tok/s/GPU)
  • 4x TP8 + EP: -0.3% at a matched 64 lanes (30.7 vs 30.8 tok/s/GPU)

It is worth contrasting that with the same search on a smaller-memory part: on a 79.2 GiB H100 no non-EP control survives at all. The difference is headroom — with 178.4 GiB per device the weights and a 256k-token KV pool fit without sharding the experts, so here EP is an optimisation rather than a precondition.

On this part the footprint stops binding altogether: no shape was refused, where the 79.2 GiB H100 run lost 12 of them to memory. What still separates the layouts is sharding width — the expert-parallel width is derived as tp × dp, so the narrow-TP arms shard nothing and scale badly.

4The knobs that bind, and the one that really hurts

Refinement moves one knob at a time off the winning topology, so any difference is attributable. Nothing improved on the defaults — these knobs constrain:

  • batch tokens 2,048: 23.4 tok/s/GPU, -48.9% — and it halves usable capacity, C* 128 → 64
  • 1 draft token: 24.3 tok/s/GPU, -46.9% — and it halves usable capacity, C* 128 → 64
  • queue-kv routing: 25.0 tok/s/GPU, -45.4% — and it halves usable capacity, C* 128 → 64
  • gpu mem util 0.7: 25.4 tok/s/GPU, -44.5% — and it halves usable capacity, C* 128 → 64
  • 3 draft tokens: 25.9 tok/s/GPU, -43.4% — and it halves usable capacity, C* 128 → 64
  • 5 draft tokens: 26.8 tok/s/GPU, -41.5% — and it halves usable capacity, C* 128 → 64
  • max seqs 64: 45.9 tok/s/GPU, +0.2%
  • prefix-affinity routing: 45.9 tok/s/GPU, +0.2%

The expensive one is batch tokens 2,048 at -48.9%. It is not a small scheduling inefficiency: it drops the servable ceiling from 128 lanes to 64. This workload's requests arrive carrying ~90,449 tokens of context, so a prefill-admission cap well below that forces each one to be chunked across many scheduler passes — the batch limit, not the GPU, becomes what paces the fleet.

5Speculative decoding, and what it does to the interactivity number

This model ships its own drafter — the catalog graph declares a dspark speculator — so draft depth is a real deployment choice, not an exotic knob. Each depth is run against the no-drafting baseline on the winning topology:

  • K=1: 24.3 tok/s/GPU, -46.9% against no drafting, acceptance length 1.81, ceiling 64 lanes
  • K=3: 25.9 tok/s/GPU, -43.4% against no drafting, acceptance length 2.9, ceiling 64 lanes
  • K=5: 26.8 tok/s/GPU, -41.5% against no drafting, acceptance length 3.51, ceiling 64 lanes

Read those percentages carefully: each arm is scored at its own usable load, and drafting moves that load. A depth whose ceiling drops is therefore scored at a lower session count than the baseline, which makes it look worse than it is at any load they share — the matched-load table below is the comparison that answers “should I turn this on”. Here the ceiling falls for K=1 (64 lanes against the baseline’s 128), K=3 (64 lanes against the baseline’s 128), K=5 (64 lanes against the baseline’s 128).

How to read the per-user rate on these rows. Under drafting the engine reports the inter-token latency of a verification step, and one step emits as many tokens as the target accepts. So the per-user token rate is the acceptance length times 1000/ITL p99, not 1000/ITL p99 — the naive reading understates a drafting configuration by the whole acceptance factor and can make the fastest configuration measured look like a floor violation. The rows above use the acceptance-scaled rate, and the explorer labels it as derived.

At matched load, drafting pays at some loads and not others (11 of 18 measured points improve on the baseline) — and it moves the interactivity cliff, so the two arms' own usable loads are not the same load. Output tok/s at each session count, with the change against no drafting:

The servable ceiling, however, falls: no drafting holds 128 lanes while K=1 at 64 lanes, K=3 at 64 lanes, K=5 at 64 lanes. Drafting spends decode compute verifying tokens, which is compute the baseline spends on concurrency — so the knob trades sessions for per-session speed. 10Terms

Each term is linked from its first use above. Hover a link for the short definition.

session-tree lane
One live agent trajectory, not one request. An AgentX lane replays a whole recorded coding session: a main turn, its sub-agent groups and their inner requests. One lane therefore puts many requests in flight, which is why the lane ladder is much shorter than a request-concurrency ramp.
expert-parallel width
tp × pcp × dp — derived, never declared. A width of 1 shards no experts, so it neither saves memory nor costs collectives. This is why adding dp rescues a layout that failed at the same tp.
C* and usable load
C* is the highest load meeting the floor; the recommendation is 0.8 × C*. The reported figures are measured AT the usable load, not read off a nearby rung of the ladder, so the throughput quoted is the throughput at the load recommended.
prefill-dominated
About 99 input tokens per output token on this corpus. Output tok/s per GPU is the ranking metric but a poor description of the machine's work here: most of each request is reading context, so a low output rate can coexist with very high total token throughput.
