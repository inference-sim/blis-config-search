Serving DeepSeek-V4.1-Flash to coding agents on 4 H100 nodes

A configuration search over 180 BLIS replay runs on 32× H100, driven by the recorded AgentX agentic traffic rather than a synthetic request shape. The winner is 4x TP8 + EP at 717.6 output tok/s (22.4 per GPU) while every user still reads at 101.0 tok/s.

BLIS discrete-event simulationblis-latency-kernel v0.3.0AgentX MVP replay (393 recorded Claude Code trajectories)32× H100 · 4 nodes

What was tested

The 12 highest-ranked of 19 valid expert-parallel and tensor-parallel layouts that fill 32 GPUs, probed up a session-lane ladder and refined one engine knob at a time — 180 runs, 12 candidate topologies, 21 refinement arms, 24 servable finalists, 12 shapes the simulator refused or that missed the floor.

What was found

This is a prefill-dominated workload: 91,926 input tokens per request against 790 output, about 116:1. Output tok/s per GPU reads low by chatbot standards because almost all the work is reading context — the winner is ingesting roughly 83,532 input tok/s.

What to run

4x TP8 + EP at 51 concurrent agent sessions (80% of the measured ceiling of 64). Expert parallelism is not optional here: no non-EP control produced a servable run (12 shape(s) refused or below the floor).

1The measurements

Each row below is one BLIS replay run. The load axis is session-tree lanes, not in-flight requests: one lane drives a whole agent trajectory that fans out into many sub-requests, so a lane is worth far more concurrency than a single chat turn.

The interactivity floor is the default 50 tok/s per user (ITL p99 ≤ 20 ms). That is a chatbot floor, and it is worth saying plainly that it may be the wrong one for an agent: these requests carry 91,926 tokens of context and their p99 time-to-first-token is 10 s, so a user waits seconds before the first token regardless of how fast the stream then runs. It is kept because it discriminates sharply on this workload — the winner holds 98.6 tok/s/user at 64 lanes and collapses to 2.3 at 128

2The operating curve, and where it stops

Throughput climbs almost linearly with lanes and then falls off a cliff. 4x TP8 + EP holds 98.6 tok/s per user at 64 lanes, and at 128 lanes per-user rate collapses to 2.3 tok/s while ITL p99 jumps from 10.1 ms to 429 ms.

The cliff is why the recommendation is 51 lanes and not the ceiling: at the ceiling there is no headroom for a burst, and this workload's bursts are whole agent trajectories waking up at once.

3Expert parallelism is load-bearing, not an optimisation

The search runs every expert-parallel candidate beside its non-EP control, because the direction is meant to be measured rather than assumed. Here the comparison is not close: every one of the 5 non-EP controls failed outright, and all 24 finalists are expert-parallel.

The failures are memory, not throughput — “No available memory for the cache blocks”, or a per-rank fixed occupancy above the 79.2 GiB device. Sharding the experts is what makes a 256k-token context fit on this part at all. It is also why the narrow-TP shapes die even with EP on: the expert-parallel width is derived as tp × dp, so a width of 1 shards nothing.

4The knobs that bind, and the one that really hurts

Refinement moves one knob at a time off the winning topology, so any difference is attributable. Nothing improved on the defaults — these knobs constrain:

  • batch tokens 2,048: 11.8 tok/s/GPU, -47.3% — and it halves usable capacity, C* 64 → 32
  • queue-kv routing: 12.0 tok/s/GPU, -46.4% — and it halves usable capacity, C* 64 → 32
  • 1 draft token: 12.0 tok/s/GPU, -46.4% — and it halves usable capacity, C* 64 → 32
  • 3 draft tokens: 13.5 tok/s/GPU, -39.7% — and it halves usable capacity, C* 64 → 32
  • 5 draft tokens: 13.9 tok/s/GPU, -37.9% — and it halves usable capacity, C* 64 → 32
  • prefix-affinity routing: 22.0 tok/s/GPU, -1.8%
  • max seqs 64: 22.5 tok/s/GPU, +0.4%

The expensive one is batch tokens 2,048 at -47.3%. It is not a small scheduling inefficiency: it drops the servable ceiling from 64 lanes to 32. This workload's requests arrive carrying ~91,926 tokens of context, so a prefill-admission cap well below that forces each one to be chunked across many scheduler passes — the batch limit, not the GPU, becomes what paces the fleet.

5Speculative decoding, and what it does to the interactivity number

This model ships its own drafter — the catalog graph declares a dspark speculator — so draft depth is a real deployment choice, not an exotic knob. Each depth is run against the no-drafting baseline on the winning topology:

  • K=1: 12.0 tok/s/GPU, -46.4% against no drafting, acceptance length 1.81, ceiling 32 lanes
  • K=3: 13.5 tok/s/GPU, -39.7% against no drafting, acceptance length 2.9, ceiling 32 lanes
  • K=5: 13.9 tok/s/GPU, -37.9% against no drafting, acceptance length 3.51, ceiling 32 lanes

Read those percentages carefully: each arm is scored at its own usable load, and drafting moves that load. A depth whose ceiling drops is therefore scored at a lower session count than the baseline, which makes it look worse than it is at any load they share — the matched-load table below is the comparison that answers “should I turn this on”. Here the ceiling falls for K=1 (32 lanes against the baseline’s 64), K=3 (32 lanes against the baseline’s 64), K=5 (32 lanes against the baseline’s 64).

How to read the per-user rate on these rows. Under drafting the engine reports the inter-token latency of a verification step, and one step emits as many tokens as the target accepts. So the per-user token rate is the acceptance length times 1000/ITL p99, not 1000/ITL p99 — the naive reading understates a drafting configuration by the whole acceptance factor and can make the fastest configuration measured look like a floor violation. The rows above use the acceptance-scaled rate, and the explorer labels it as derived.

At matched load, drafting pays at some loads and not others (10 of 18 measured points improve on the baseline) — and it moves the interactivity cliff, so the two arms' own usable loads are not the same load. Output tok/s at each session count, with the change against no drafting:

Drafting spends decode compute verifying tokens, which is compute the baseline spends on concurrency — so the knob trades sessions for per-session speed. Set it from which of those you are short of: at a fixed session count below the drafting cliff it is close to free throughput, and above that cliff it costs you the sessions.

The acceptance lengths are measured, not assumed: they come from inferencex-golden-al (b200) in blis-registry, keyed by this model, drafter, depth, thinking mode and workload category. They were measured on another part and reused here; the profile set states that acceptance depends mostly on the model, drafter and workload rather than the chip, and asks that the reuse be recorded, so it is recorded on every row.

6What doubling the cluster buys

The same search at 32 and 64 GPUs on H100 makes the scaling explicit. Going from 32 to 64 GPUs multiplies fleet throughput by 1.04x (717.6 to 747.6 output tok/s) and the servable ceiling by 1.00x (64 to 64 lanes).

Per-GPU efficiency therefore falls from 22.4 to 11.7 tok/s/GPU (0.52x). Capacity scales but efficiency does not: the second half of the cluster is doing real work — the ceiling genuinely doubles — while each GPU does less of it. For a fixed interactivity target that is the honest trade, and it means the larger cluster is the right buy only if you need the extra 0 lanes of capacity, not if you are chasing tokens per GPU.

4x TP8 + EP at 51 concurrent agent sessions, on the h100 deployment flags in the table below. That is 717.6 output tok/s across 32 GPUs (22.4 per GPU) at 101.0 tok/s per user and ITL p99 9.9 ms.

Leave the engine knobs at their defaults. None of the refinements helped, and the routing profiles in particular cost capacity on this traffic.

10Terms

Each term is linked from its first use above. Hover a link for the short definition.

session-tree lane
One live agent trajectory, not one request. An AgentX lane replays a whole recorded coding session: a main turn, its sub-agent groups and their inner requests. One lane therefore puts many requests in flight, which is why the lane ladder is much shorter than a request-concurrency ramp.
expert-parallel width
tp × pcp × dp — derived, never declared. A width of 1 shards no experts, so it neither saves memory nor costs collectives. This is why adding dp rescues a layout that failed at the same tp.
C* and usable load
C* is the highest load meeting the floor; the recommendation is 0.8 × C*. The reported figures are measured AT the usable load, not read off a nearby rung of the ladder, so the throughput quoted is the throughput at the load recommended.
prefill-dominated
About 116 input tokens per output token on this corpus. Output tok/s per GPU is the ranking metric but a poor description of the machine's work here: most of each request is reading context, so a low output rate can coexist with very high total token throughput.
These are simulator predictions from the blis-latency-kernel backend — spot-check against the real llm-d measurements in curvebender-tools/reports before acting.
